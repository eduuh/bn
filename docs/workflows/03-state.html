Note 04

What bn writes down, and where it survives

Everything the system remembers sits on one of three axes: the branch, the repo, or the person. Which axis a thing lives on decides whether it survives worktree cleanup — and that single distinction answers most "where did my note go" questions.

Three scopes

Anatomy of a branch note

One file, note.md, at <notes_root>/<machine>/<repo>/<branch>/note.md. Branch slashes are dashed into the key, so feat/x becomes feat-x. resolver/paths.rs:21, :29 · resolver/context.rs:205

The split between the two halves is strict. Frontmatter holds the structured item lists; the body holds prose only — ## Goal, ## Progress, and optionally ## Notes / ## Test Cases / ## Plan. crates/bn-core/src/model.rs:132, :399 · commands/body.rs:55

Handoffs

handoff.json is authoritative, handoff.md is the human mirror; both sit beside the note and are written atomically. The packet is composed from the note — goal, the last five progress bullets, open todos, blockers, made decisions, ## To Ask, directives — with narrative, deferred decisions and an explicit priority queue supplied by the author. crates/bn-core/src/handoff.rs:28, :33, :116, :194

Missing handoff is not an error

When no packet exists, every reader composes one live from the note rather than failing — MCP, CLI and web alike. Only a genuinely missing note fails. crates/bn-mcp/src/server.rs:416-420 · cmd/agent.rs:794 · bn-web/src/api.rs:415

Reference notes: knowledge that outlives the branch

Two stores, one engine, split by Scope. Scope::Repo resolves to <notes>/<machine>/<repo>/reference/**.md — a sibling of the branch-note directories, not under any branch. Scope::Global resolves to <personal_root>/references, with no machine segment. crates/bn-core/src/references.rs:27 · paths.rs:294, :307

"Outliving the branch" is literal geometry: a branch note dies with bn wt cleanup; reference/ sits one directory up and survives. The repo template bakes in the evidence convention — every bullet carries (src: path, date) — and appends are deduplicated document-wide, so appended:false means "already known" rather than "failed". references.rs:91, :341, :348-355, :365

Two files named events.jsonl

Same primitive, different meanings, different trees. Conflating them is the easy mistake.

events.rs:119 · paths.rs:167-180, :261 · commands/error.rs:12-29

Records are flat — {kind, ts, ...flattened} — so a new kind needs no migration. Every append is a single write under a local-disk lock, because O_APPEND atomicity does not hold on the 9p mount WSL uses. Payload keys named kind or ts are renamed to kind_field/ts_field so they cannot shadow the envelope, and unparseable lines are skipped on read. events.rs:19, :139, :169, :196-203, :250

Things that will mislead you

  • The goal is prose, not a field. bn_goal edits the body and goal_text reads back the first non-blank line. A goal string containing \n## Goal once doubled the body on every call. render.rs:127-140
  • bn_links_add is the one tool that does not fail closed. With no branch resolved the link is stored without a repo, because losing a capture over the client's working directory is the wrong trade. server.rs:218-232
  • There is no MCP path to write the global standards store. bn_ref_append is repo-scoped only; bn_ref can read global.
  • harnesses and models record themselves. Every note mutation calls record_session, so the note knows which agents touched it without anyone saying so. model.rs:434
  • A 32 MB read ceiling exists because of a real 4.2 GB note.md. A dispatch bug appended a seed prompt to the same todo every pass, and every sweeping reader OOM-killed the dashboard. store.rs:41-53
  • bn done <text> searches todos and done-when together, so a substring can tick an acceptance criterion you meant to leave open. commands/todo.rs:200-215
  • Findings and backlog are append-only JSONL in state_dir: findings keep history per source; backlog is log-structured with latest-line-wins per (repo, id) plus periodic compaction. findings.rs:60 · backlog.rs:16-19, :570

Not verified

  • The link, q, pct, est, actual and notes fields on Item are documented as primarily daily-goal and calibration features. Not every producer was traced, so which of them ever appear on a branch-note todo in practice is unconfirmed.
  • How split-layout note.yaml notes get migrated in bulk — only that save retires the sibling to .yaml.bak on the next write.
  • The exact timestamp format bn log-progress prepends to a progress bullet; only the core append path was read, not the CLI formatting.
  • Whether bn_sync proposals are ever auto-applied elsewhere. The MCP tool itself is read-only.
  • Whether the global standards store is reachable from the web API, or only via CLI and MCP.
