Note 02

The pipeline and its gates

Nine stages are declared. One is driven. Two unrelated mechanisms are both called "gate", and only one of them can stop a transition. Getting these three facts straight is most of what it takes to read the pipeline code correctly.

The nine stages

Stage is a nine-variant enum ordered pickup→learn so that Ord comparisons and next() follow the flow. Stage::DEFAULT is Pickup — what a worktree with no recorded transition folds to. crates/bn-core/src/pipeline/stage.rs:23, :46, :59

#StageWhat happensDriven by
1pickupTask leased into a fresh, uniquely-branched worktree—
2investigateResearch problem + codebase; write findings for the planner—
3planConsume findings, propose fix + done-when, submit for review—
4consensusReviewer agents vote; quorum advances, no-consensus pulls in a human—
5executeImplement exactly the agreed plan—
6validatebn verify — build + test + lint, re-run after any rebase—
7critiqueFresh-context adversarial diff review vs the acceptance criteriacritic loop
8shipOpen / mark-ready the PR; orchestrator lands it on merge—
9learnFold the outcome + reflections back—

The descriptions come from the enum's own doc lines. crates/bn-core/src/pipeline/stage.rs:24-41

Everything in the "driven by" column had to be established separately, because the enum does not encode it.

There is no exit predicate

Nothing in Stage says when a stage is finished. A stage changes when a caller invokes stage::transition. Only critique has machinery deciding completion: it exits on the critic's verdict. crates/bn-core/src/pipeline/critic.rs:42

The others advance only by hand, by the stage agent calling the transition itself, or, for execute, when the critic sends work back. Stage::Consensus appears exactly once outside stage.rs, mapping the review attention type; Pickup, Validate, Ship and Learn appear nowhere else at all. crates/bn-cli/src/cmd/attn.rs:669

Why nothing walks the stages for you

Not an oversight. Validate, critique and ship each own their own machinery, and a second driver would give a single step two owners. Investigate, plan and execute once had one, a sweep that filed each stage as background work; it was removed, so they now move when you or the stage agent move them.

Two things called "gate"

This is the single most misread part of the pipeline. The two gates sit in different places, are checked by different code, and fail in different ways.

Gate A — the SMART gate

is_smart_gated is true for exactly one destination: Stage::Investigate. It keys on where the transition lands, not on the (from, to) edge. crates/bn-core/src/pipeline/gate.rs:98-100

It is blocking, and it is the only enforcement point in the whole state machine. transition refuses before writing anything — the note keeps its old stage and no event is appended. crates/bn-core/src/pipeline/stage.rs:275-293 A refusal stamps smart:fail, bumps smart_tries, and raises one idempotent attention item keyed attn:smart:<id> carrying gap codes and suggested fixes. After MAX_IMPROVE_TRIES = 3, or immediately if the verdict needs a human, the task goes smart:stuck and the item is re-raised as manual. gate.rs:32, :198, :279-371

The judgement itself is smart::check over five dimensions, returning stable gap codes — no_repo, too_terse, vague_verb, no_done_when, no_estimate, too_large, blocked, not_relevant, no_date, stale_date. crates/bn-core/src/smart.rs:206-340

Three cases are admitted without judgement: an ungated stage, an Ungoverned worktree with no governing task, and machine-minted work. gate.rs:44-49, :160

Why the three-strike short-circuit exists

A real incident: one task accumulated 3,899 tries, driving roughly one store write every 23 seconds. crates/bn-core/src/pipeline/gate.rs:173-191

Gate B — the hold policy

GatePolicy::{Auto, Hold} is the human gate. It is resolved into every StageProfile, and StageProfile::is_held answers whether entering a stage waits for a human. crates/bn-core/src/pipeline/profile.rs:37-60, :160-164

Nothing enforces it now

Its only caller was the pipeline sweep, which refused to start a held stage until a plan review was approved. The sweep was removed along with the machine-wide queue, so a hold is computed, ratcheted and shown, but blocks nothing: a hand-typed bn dispatch or bn pipeline set never saw it, and nothing else asks.

Routing and profiles

route::classify is a pure function returning a RoutePlan. Its trust boundary is expressed as a type: Declared inputs (bn-authored — estimate, done-when count, smart_tries, pin) may narrow or widen the route; Observed inputs (labels, title shape, evidence count, blockers) are widening only, and a test asserts it. pipeline/route.rs:79-106, :413

RouteStagesFanoutReviewersCritic rounds
Mechanicalinvestigate, execute000
Standardinvestigate, plan, execute3—3

Thresholds: DEEP_EST_MINUTES = 180, MECHANICAL_EST_MINUTES = 30; five or more done-when criteria, two or more smart_tries, or three or more evidence items all push to Deep. Any guarded task — one with non-empty risk_reasons — appends critique, forces Hold, and floors reviewers and rounds at 3. route.rs:156-214, :257-292

Nothing consumes this yet

RoutePlan is computed and serialized by bn pipeline route, but no Rust caller was found that reads reviewers or critic_rounds. The module says so itself. pipeline/route.rs:8-9 · cmd/pipeline/route_view.rs:3-5

What a launcher actually reads

profile::StageProfile is the thing consulted at launch: model, effort, harness, skill, references, gate — plus a Provenance naming which layer won. Six layers fold from low to high: 

built-in defaults
  → [pipeline.stages.<S>]
    → [repo.<R>.pipeline.stages.<S>]
      → task meta
        → note decision
          → CLI flag

Built-in model choices: plan and critique get claude-opus-4.8 at max effort, investigate gets gpt-5.4 at high, everything else gpt-5.4-mini at medium. pipeline/profile.rs:176-182, :221-252

The gate ratchet

One field breaks the last-writer-wins rule. Every layer below the CLI may only tighten auto → hold; an attempt to loosen is recorded in gate_ratcheted_from rather than applied. profile.rs:254-272

The reason is concrete and worth stating plainly: bn_add exposes the decision section over MCP. Without the ratchet, an agent sitting behind a hold could write pipeline: execute gate=auto into its own note and release itself. profile.rs:19-24

How a transition is recorded

Two records, and they do not travel together. The durable current stage is note frontmatter (stage: Option<Stage>); every transition is also appended to the event log as kind pipeline_stage. crates/bn-core/src/model.rs:139 · pipeline/stage.rs:18, :183-189

Order inside transition: acquire the note lock, gate-check, save the note, append the event. stage.rs:272-293 Resolution for a legacy note is a three-step fallback — frontmatter, else the latest event, else Stage::DEFAULT. The CLI labels that last case as (default — none recorded) rather than presenting a guess as a fact. stage.rs:222-226 · cmd/pipeline/target.rs:23-33

The history is machine-local

The event log lives at state_dir()/events.jsonl, and state_dir() is personal_root/<machine>/state. Frontmatter syncs with the notes repo; the transition history does not travel between machines. crates/bn-core/src/events.rs:120 · resolver/paths.rs:261-262

The critic stage

"Fresh context" here is not a convention — it is enforced by a function signature. critic_packet(diff, done_when, pr_url) has no parameter through which the approved plan could leak. pipeline/critic.rs:1-8, :73

Mechanically, four separate measures:

  • A new branch critic/<exec-branch> is cut off the execution head into its own worktree. crates/bn-cli/src/cmd/critic.rs:138-143
  • The diff is computed by the driver, not the agent, as three-dot base...HEAD. critic.rs:157-160
  • A plan-free note is seeded whose goal is only "critique this diff", so the critic cannot recover the plan with bn --cat. critic.rs:161-181
  • The harness launches --fresh with a brand-new session id and zero prior turns. critic.rs:227-232

The loop is bounded at DEFAULT_MAX_ITERATIONS = 3: a FAIL on rounds 1 and 2 sends it back to execute, a FAIL on round 3 escalates to a planning attention item. pipeline/critic.rs:12, :42-48

The iteration counter is stored nowhere. It is parsed back out of the live attention item's title, explicitly so that no attention-schema change was needed. critic.rs:52-67

Things that will mislead you

  • Two lowercase vocabularies. Stage (nine, durable) versus status::Phase (four, inferred, persisted nowhere). The JSON field is named phase precisely so stage stays unambiguous. status.rs:7-19
  • Mechanical keeps investigate only to preserve a gate. Dropping it would delete the SMART check from the dispatch path; a test pins this. route.rs:258-261, :386
  • The board shows the skill that ran, not the stage's default. It reads back a skill: note decision, because printing the default would be "a confident lie". stage.rs:228-252
  • attn start can set a stage. It maps an attention task_type onto a stage, so a review item lands the worktree in consensus. crates/bn-cli/src/cmd/attn.rs:665-673

Not verified

  • Exit criteria for pickup, consensus, validate, ship and learn are taken from doc comments only — no code was found that enters or leaves them. Non-Rust drivers were not exhaustively searched beyond one grep of *.md, which found only config/prompts/plan.md:41.
  • profile.rs:105 and resolver/config.rs:964 reference bn pipeline preview, but PipelineCmd has no Preview variant. Likely doc drift; not confirmed whether it ever shipped.
  • gate.rs:96-97 claims the hold policy is "asked after this one; see stage::transition for the ordering", but transition checks only the SMART gate. Either the comment is stale or the ordering is intended and unimplemented.
  • Consensus and quorum were not traced end to end — only that dispatch_plan_reviewers defaults to 3 with a strict-majority quorum (plan_review.rs:24, :516).
