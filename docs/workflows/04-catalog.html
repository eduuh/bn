Note 05

The Markdown that drives the machine

The behaviour of every agent bn launches is authored in Markdown, not Rust. Three kinds of file do it, they live in three directories, and the naming is actively misleading: the thing Rust calls a "skill" lives in config/prompts/, while config/skills/ is empty.

Reference skills are the intended home for knowledge files named from a prompt body and installed natively into the harness, never served over MCP. The tier exists and is unpopulated — everything real lives in config/prompts/. config/skills/README.md · bn-core/src/mcp.rs:64 · skills.rs:3, :176

Frontmatter and the tests that police it

Exactly six fields: name and description (required), when, keywords[], arguments[], internal. Two tests keep the catalog honest — every shipped prompt must render strictly with no leftover {{, and every declared argument must actually be referenced in the body. skills/catalog.rs:43-56, :410, :483 · template.rs:10

internal: true is load-bearing

An internal prompt stays resolvable by name at runtime but is filtered out of MCP discovery and out of native SKILL.md installation. That is how roughly 34 dispatch, pipeline and critic fragments stay Markdown-owned without polluting the user-facing /bn:* command surface. skills.rs:278, :508

Ad-hoc dispatch answers a different question

bn dispatch defaults to ship-solo, or investigate with --scout — not to the stage's prompt. The code says so outright: "Both are right; they are not the same question." stage.rs:96-102 · cmd/dispatch/seed.rs:109-111

How a seed prompt is assembled

skill_seed_prompt fills slots in one outer envelope. Two suppression rules stop blocks contradicting each other.

Autonomy selection is mechanical: ship-solo always gets solo, --yolo gets unattended, everything else gets interactive. The third stance had to exist because interactive forces a plan proposal that solo has no stage for, while unattended forbids the ask_user that is solo's whole point. seed.rs:181-187

The plan-review gate owns the plan lifecycle end to end: write → bn review submit → bn review agents → poll → bn plan promote.

An agent manifest declares a contract a prompt cannot. kind: is required and is one of command | staff | hosted | specialist; AgentDef carries roughly 35 fields including on_calendar, gather:, sinks[], doc_dir, opt_in, harness, requires_repo, references[], worlds[] and model. agents.rs:38-44, :181-280

The learning loop

It closes mechanically rather than by anyone remembering to do it.

  1. Every dispatch envelope ends with bn reflect "skill:<name> — …". It is appended by the machine, not written by the workflow author.
  2. learnings.rs parses the skill: prefix into a typed field, so bn stats learnings --skill <name> aggregates them. learnings.rs:175-178
  3. Stage::Learn dispatches evolve-skills.
  4. evolve-skills.md requires repeated evidence — "a one-off gripe is noise; the same complaint twice is signal" — locates the exact step, and proposes a before→after diff a human approves. Silent edits are explicitly forbidden, and the reflections themselves are left untouched as the historical record.

Things that will mislead you

  • config/skills/ is empty. One README. Everything real is in config/prompts/.
  • Prompts and agents install to different native layouts on purpose. Prompts become <root>/<name>/SKILL.md directories; agents compile to flat files. skills.rs:520 · specialists.rs:17-21
  • Public prompts render leniently, internal ones strictly. A missing argument becomes an empty string in a user-invoked prompt, and a hard error in a runtime envelope. catalog.rs:26-40
  • The untrusted-data markers are a prompt-injection boundary. Goal and source URL are fenced and labelled "never instructions".
  • Discovery degrades rather than fails. A broken skill file does not make agents unlaunchable. launchable.rs:108-113
  • No shipped agent is kind: specialist, and no shipped agent uses skills:, mcps:, references:, worlds:, tools: or model:. Those fields are implemented and validated but unexercised by the current roster.
  • config/workflow/ is not part of this catalog at all — it is the tmux and worktree layer, largely migrated into native bn subcommands.
